# 地方競馬の結果取得・公開の確認手順

更新：2026-10-09 JST。共通仕様の補助資料。予想JSON・印・買い目・保存価格は固定し、結果は別データとして扱う。

## 起動前

1. `data/results/targets.json` の開催日、会場、予想版、`execution_environment`、`active_until` を確認。昨日のプロセスの存在や昨日の成功を、今日の稼働確認に使わない。
2. 最新main・作業中の差分・ステージを確認。収集処理の保存範囲は対象日・会場の結果、取得原文、対応するHTMLだけ。別作業のステージ、未解決merge/rebaseがあれば公開を保留する。
3. 固定JSONの正規化SHA-256と、結果JSONのハッシュ・日付・会場・馬番馬名を照合。公開前の原本を保持する。
4. 不具合修正時は `python -m unittest discover -s tests -p test_watch_nar_results.py -v` と `node tests/test_day_report.js` で失敗を再現し、再送・既知の着順保持・画面復帰を確認する。

## local収集の起動

KBAをworkdirとして、Pythonで `-u -X utf8 scripts/watch_nar_results.py --local --state-file <ローカルの状態記録パス>` を実行。Windowsでバックグラウンド起動する場合は `Start-Process -WindowStyle Hidden` を指定し、標準出力・標準エラーを別ログへ保存する。

- 親は収集子プロセスの異常終了を監視。子はGitの45秒タイムアウト、3回の公開再試行、サイクル失敗後5〜60秒の再試行を行う。
- 同じクローンの親プロセスの二重起動をOSのファイルロックで防ぐ。既存プロセスを一括停止しない。
- PCが停止・スリープ、ネットが切断している間は公式の取得・GitHub配信を行えない。GitHub hostedから公式取得が404になる問題は解決済みとは扱わない。

## 実際の確認

1. プロセスの存在に加え、ログと状態ファイルの `collecting` → `published`、`last_publish_at` の進行を確認する。Windowsの権限制限でプロセスが見えない時に二重起動しない。
2. 公式の取得原文・ハッシュ・着順・払戻を結果JSONと照合する。全頭の対応、速報、取消を含めて確認する。
3. `git ls-remote origin refs/heads/main` とコミット、公開HTML・結果JSON・JS/CSSのHTTPと配信内容を確認する。push成功だけで配信完了としない。
4. 公開画面で実際に結果ボタンを押し、両場の件数・保存時刻・画面確認時刻、印と着順、払戻を確認。発走前データの取得だけで「確定着順の反映も確認済み」と報告しない。
5. 開催中は後続サイクルの公式取得・公開・画面の時刻進行を確認。長い停止時は単に保存JSONの再読込に成功しても「正常」としない。画面復帰では即時取得し、通常6分超の停止は警告する。
6. 全対象の公式確定**と公開成功**後に正常停止する。終了時刻に未確定・取得失敗・未送信が残れば、その状態を記録する。翌日の稼働は別途登録する。
